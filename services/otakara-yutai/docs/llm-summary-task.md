## 1. 最初に守ること（禁止事項）

タスクファイルの `description` は**外部の優待情報サイトの掲載文そのもの**です。
掲載元の規約は、私的使用を超える蓄積・公開・再配布を禁じています。
そのうえ、このリポジトリ（kabulab-cf）は **public** です。

1. **タスクファイルも結果ファイルも、リポジトリにコミットしない。** ブランチを作らない、PR にしない、push しない。
   置いてよいのは `services/otakara-yutai/data-scripts/data/`（gitignore 済み）の下か、リポジトリの外だけです。
   書き出し・取り込みのコマンドは、それ以外の場所を指定すると止まります。
2. **公開される場所に置かない・貼らない。** Gist、公開 Issue / PR / コメント、公開のチャット、ログを共有する外部サービスは不可。
   コミットメッセージ・PR 本文・作業ログに `description` の文面を引用しない。
3. **結果に `description` を含めない。** 結果に書くのは下の 4 つのキーだけです（余計なキーがあると行ごとはじかれます）。
4. **掲載元サイトを見に行かない。** スクレイピングや追加の検索で情報を補わない。判断材料はタスクファイルの中だけです。
5. **推測で埋めない。** 金額が決められなければ `null`。架空の商品名や条件を足さない。
6. 作業が終わったら、不要なエージェント側コピーを消す。運用者が固定した原入力・結果・PRE/POST・unknownの証跡は保全する。

## 2. 作業の流れ

```
[運用者] pnpm yutai:summary:export            → data-scripts/data/summary-tasks/tasks-YYYY-MM-DD.jsonl
            │  (非公開の経路で渡す。コミットしない)
            ▼
[明示したレビュー担当] この文書に従って 1 タスク 1 行の結果 JSONL を作る
            │  (非公開の経路で返す。コミットしない)
            ▼
[運用者] 保存入力で共通planSummaryImportを検証し、tasks/results全fileのSHAを固定
[運用者] 下記の明示manualコマンド（共有owner・物理PRE/POST・通常原子取込）
```

```sh
nix develop --command pnpm yutai:summary:local --state-dir <私有state> --limit <1〜60群> \
  --reviewed-tasks <私有tasks.jsonl> --reviewed-tasks-sha256 <全bytesのSHA256> \
  --reviewed-results <私有results.jsonl> --reviewed-results-sha256 <全bytesのSHA256>
```

4引数は全指定、`--allow-model`とは排他。通常file・所有者・0600・8MiB以内・全SHA・現契約を照合し、指定task集合を切り詰めず、issuer codesをSQLで先限定して同issuerの全tierを読む。inactive・対象消失・内容/recipient/行数の変化は停止する。結果を機械compilerの別結果へ置換せず、原file全bytesとSHA・reviewed件数を通常PRE/POSTへ保管する。モデルprotocol・token・モデルidentityを作らず、日次cursorは読取も更新もしない。

これはLinuxで明示する手動入力であり、日次機械入口はreviewed入力とモデル許可を依存生成前に拒否する。共有writer未初期化・owner/pending未閉鎖は停止し、新state-dirへ替えて再送しない。受入済みMacの固定runtime/env/pinは変更しない。通常のMac月次実行をこの手動入力へ自動切替しない。新しい有料モデル呼出やLLM定期処理は追加しない。

- タスクの単位は `(銘柄コード, 掲載文)` です。同じ文言の行（権利月違い）はまとめて 1 タスクになっています。
- はじかれた行は D1 に書かれず、前の値のまま残ります。理由を見て、その行だけ作り直してください。
- エージェント自身が書き出しを実行する運用にする場合も、出力は gitignore 済みの場所に置き、上の禁止事項を守ること。
  本番は保存結果・入力・通常planを運用者が受入した後だけ実行する。旧standalone dry-runは全active行を読むため、有限cohort検証は保存入力で共通pure plannerを使う。

```json
        "required": ["minShares", "recordMonth", "recordDate"],
        "properties": {
          "minShares": { "type": "integer", "minimum": 1 },
          "recordMonth": { "type": "integer", "minimum": 0, "maximum": 12 },
          "recordDate": { "type": ["string", "null"], "description": "単発の実基準日YYYY-MM-DD。NULLは通常月または随時。日付を推測・変更しない" }
        },
        "allOf": [{ "if": { "properties": { "recordMonth": { "const": 0 } } }, "then": { "properties": { "recordDate": { "const": null } } } }]
      },
      "description": "実際の最低保有株数と権利時期。0は公式随時専用でrecordDate=null必須、1〜12は実月。重複を除いた組合せ"
    }
  }
}
```

`description` の先頭行が `【種別："..."】` の形のとき、 `"..."` の中身は
掲載元ページの表見出し（この優待の種類・条件の原文）です。優待の種類
（割引券・抽選・選択肢など）の判断材料として読んで構いませんが、
`【種別：` という記号列そのものは結果に書き写さないでください
（書くと `internal` 違反ではじかれます）。

`recipients` の全行に共通する1回分の額面だけを回答してください。株数条件が
混在する群や、月ごとに金額が異なる群では、最大額や最長保有条件を選ばず
`estimatedValue: null` にします。取り込み時に受取条件が変わっていた結果は
`stale` としてはじかれるため、現在のタスクを再発行してください。

## 4. 出力: 結果ファイル（JSONL、1 行 1 タスク）

```json
{
  "$schema": "https://json-schema.org/draft/2020-12/schema",
  "title": "SummaryResult",
  "type": "object",
  "additionalProperties": false,
  "required": ["taskId", "contractVersion", "shortSummary", "estimatedValue"],
  "properties": {
    "taskId": { "type": "string", "description": "タスクの taskId をそのまま" },
    "contractVersion": { "type": "string", "description": "タスクの contractVersion をそのまま" },
    "shortSummary": { "type": "string", "minLength": 1, "maxLength": 256 },
    "estimatedValue": { "type": ["integer", "null"], "minimum": 1, "description": "優待 1 単位あたりの推定金額 (円)。決められなければ null" }
  }
}
```

- 1 タスクにつき 1 行だけ。同じ `taskId` を 2 回書くと、**両方**はじかれます（片方が形の崩れた行でも同じ）。
- 行の順序は自由。全タスクに答えなくてもよい（答えなかったタスクは「未回答」と数えられるだけ）。
- ファイル全体を JSON 配列にしない。コードフェンスや説明文を混ぜない。文字コードは UTF-8。

## 5. `shortSummary` の規則

公開する優待内容のテキストです。詳細は全文、一覧は既存の80字clipと省略記号で表示します。256字は全種類の内容や重要条件を保持する共有契約の上限であり、DBの物理制約ではありません。新しいUIや生の`description`公開は追加しません。上限変更前の保存snapshot全7,728行では最長119字で、上限変更だけで新たに有効になる既存要約はありません。この実測は保存時点の母集団に限り、未確認の旧長文の受入証明には用いません。新しい結果は現行taskから全共有検証を通します。
掲載文から「何が・どれだけ」もらえるかという事実だけを抜き出して、自分の言葉で短く書きます。

### 取り込みで機械的にはじかれる規則（必ず守る）

| 規則 | 内容 |
|---|---|
| `empty` | 空（空白だけも不可） |
| `too_long` | **256 字を超える**（NFKC 正規化と前後の空白除去の後の文字数） |
| `annotation` | 注記記号 **`※` `■` `◆` `◇`** のどれかを含む |
| `prose` | **`です。` `ます。` `ください` `いたします`** のどれかを含む（説明文調） |
| `internal` | 内部 marker **`【種別：`** を含む（タスク掲載文先頭の表見出し行の記号列を書き写さない。見出しの読みやすい条件文言自体は書いてよい） |
| `verbatim` | 40 字以上あり、その全体が掲載文にそのまま含まれている（掲載文の書き写し） |
| `summary_conditions` | 選択・保有・抽選・応募の重要条件が欠落 | 同じ条件を要約に残す |
| `summary_ungrounded` | 要約の単位付き数値（円額・枚数・袋数・パック数・セット数・冊数・ケース数・リットル数・室数・杯数・台数・箱数・ゲーム数・ホール数・商品数・品数・缶数・足数・親等・種類数・株数・年数・日数・か月の期間・暦の月・回数・点数・人数・部数等）が掲載文・実受取条件と一致しない。桁の表記揺れと観測済みの重量単位kg/Kgだけを同義照合し、掛算・年間換算や別条件の株数を補わない。人数「20名」で率「20%」は根拠づけられない |

全角の英数字は取り込み時に半角へ揃えるので、どちらで書いても構いません。
掲載文と同一の製品語「3Dプリンター住宅」「1デーパスポート」に含まれる数字だけは数量として扱いません。製品語ごとに掲載文の一致を必要とし、片方があるだけでは別の製品語を認めません。数字や製品語の変更、後続の枚数・金額は通常の数値検証を通します。
周年は、正準の正の安全整数Nによる「N周年」が掲載文と完全に同じ場合だけ同じ周年字句として照合します。別の周年数や数値の部分一致・不正表記は採用せず、周年数を円額・株数・保有年数の根拠にしません。旧契約`.3`結果は保全し、新版の現在taskを選定し直して別結果を検証します。
継続保有の定義内の株数は、現在の受取tierの株数と分けます。既知の定義文全体と一致する「継続条件:」句に限り、期間・両月末・同一株主番号・株数以上・連続記録回数を原文へ束縛します。不完全な句、別の時点・名義・数値、追加例外は拒否します。現在の株数が定義閾値未満、株数/月contextが空、現在月が定義月以外でもHOLDし、句外の株数は従来どおり現在recipientと照合します。公開factsの適用資格を認定するものではありません。旧`.4`入力は保全し、fresh taskと別途意味レビューした結果を使います。
掲載文に「同一株主番号」または「同一の株主番号」が実在する場合に限り、この同義2表記の「一株」を数量として扱いません。比較時だけの処理で、保存する文面・保有条件は変えず、実際の一株・株数や原文にない同語は引き続き拒否します。
製品語の外の金額・率・数量・株数・保有条件は引き続き同じ根拠を必要とします。原Unicode省略記号「…」は数字・小数点・桁区切りの直後でない数値前の区切りだけとして照合し、ASCII小数や数値間の省略から断片を採用しません。

### 書き方の指針

- 目標は **30 字前後、長くても 40 字**。256 字は上限であって目標ではない。全種類の内容・重要条件・両数量を保持するために必要な長さは許容する。
- 「優待の種類 + 金額や数量」を先に書く。例: `QUOカード 1,000円分` / `自社店舗 10%割引券 5枚`。
- 40 字に収まらないときは、上から順に削る:
  1. **保有期間で内容が分かれるなら条件の違いを保持**する。収まらなければ「保有期間に応じたカタログギフト」のようにし、最大額だけで全受取条件を代表させない。
  2. 贈呈時期・有効期限の詳細は省く。受取条件や選択制など内容の意味を変える条件は残す。
  3. 数字は半角にする。
  4. 複数の選択肢は種類をまとめ、選択制を示す。代表を全体の価値として書かず、`(3点から選択)` のように添える。
- 種類がはっきりしない掲載文は、主要な語を残して簡潔にする。架空の商品名を足さない。
- 割引率の `%` の数字は掲載文の数字をそのまま写す（掲載文の「10%」を「20%」と書かない。掲載文の人数「20名」は率の根拠にならない）。
- 「足」は掲載文の同じ数値・同じ単位だけで裏づける。「足目」「足袋」から数量を切り出さず、別数量・枚数・漢数字や原文にない足数で補わない。
- 「品」「缶」は掲載文の同じ数値・同じ単位だけで裏づける。「品目」「品種」を「品」の数へ、「缶目」「缶詰」を「缶」の数へ読み替えず、尾など未対応単位や数量の推定・換算は採用しない。
- 「日」「か月」は掲載文の同じ数値・同じ単位で裏づける。「か月」「ヶ月」「カ月」「ヵ月」は同じ月期間として照合し、数値・以上/未満等の条件は変えない。期間の「か月」を権利月の「月」で補わず、年・月・日への換算もしない。
- 冊子などの数量「部」は掲載文の同じ部数で裏づける。別の部数・単位に置き換えない。
- 単位や数量しか分からないときは `優待品 10枚` のような一般語で書く。

掲載文と同じ「100株以上200株未満」のような完全な株数範囲は、下限が全受取条件の必要株数と一致するときだけ採用します。上限だけの記載、別の段階の範囲、上限や以上・未満の変更は採用しません。

選択・保有・抽選・応募条件はローカル生成だけでなく外部結果の取込でも検証します。実対象の【期間保有】見出しと「継続保有期間について」内の同じ対象期間の独立した名簿回数定義が明示された場合だけ、別期間の「保有とは、株主名簿…同一株主番号…N回以上連続して記録されたことをいいます」という全行定義ラベル、または「保有:連続N回以上」だけの名簿回数定義ラベルは対象期間として要求しません。本文の例外条件や抽選・応募・選択条件は残し、対象期間の見出しがない場合や曖昧な説明は従来どおり保留します。単独の「5年以上」などの期間条件は同じ閾値を残してください。応募・申込が必要な場合はその行動も明記し、「抽選」「当選」だけで代用しないでください。複数の保有段階は金額を代表させず「保有期間に応じた」と明示できます。条件を落とした既存要約や原文・各行の実受取条件に裏づけられない数値を含む既存要約は、自動で再作成に回し、月次の持越しでは要約・金額・出典を未確認に戻します。

## 6. `estimatedValue` の規則（円・正の整数・優待 1 単位あたり）

優待利回りの計算に使われます。**過大評価は利用者を誤誘導するので、迷ったら `null`** です。
`0` や `1` などの「とりあえずの値」は不可（スキーマで `1` 以上に制限しています。0 円相当なら `null`）。

金額は**企業が明示した、対象の受取条件に合う優待全体の1回分の円建て額面**だけを入れます。
商品相場・転売価格・選択肢の代表額を推定しません。確実に受け取れる
か分からないもの（人数限定で割当方法の明示が無い、購入・契約などの対価条件が
ある）は金額が書いてあっても `null` です（要約には特典の内容を書いて構いません）。

### 金額を入れるもの

- 企業が **「○○円相当」「○○円分」と明示している**もの。金券・カタログギフト・自社商品・食品のどれでも、その額面を使う。
- 金券の単価と1回分の枚数が**同じ句・同じ優待条件で明示**されている場合の、単価×枚数。離れた商品の単価と数量を組み合わせない。
- ポイントは、付与数と**「1ポイント＝○円」の厳密な換算率が同じ句に明示**されている場合だけ換算する。カタログ型であっても1ポイント＝1円とは推定しない。
- 「1 回 ○○円相当（年間 △△円相当）」なら **1 回分の ○○**。年間額だけから回数で割った値を作らない。
- **桁を厳密に**: `20万円相当` は `200000`、`2千円` は `2000`。

### `null` にするもの

- **割引・値引き**（`○%割引` `○円引き` `優待価格`）。受け取る金銭ではないため。割引券であっても額面の金券表現が無ければ `null`。
- **会員権・施設利用・サービス利用などの権利**（「○○円相当」と書いてあっても `null`）。
- 買い物で貯まる / 付与される**販促ポイント**、`ポイント○倍`、`○○ポイント還元`。
- 概算（`約`・`≒`）、選択肢、未価格の付帯品がある優待。部分額や代表の品を優待全体の金額にしない。
- 複数の品の額面の任意の加算、別の株数・保有期間・権利月の額面、年間合計、転売・買取相場。
- 寄付・社会貢献・抽選。抽選の賞品額・最高賞品額・賞金総額は入れない。固定の特典との併記でも、優待全体を一意に価格付けできなければ `null`。
- **外貨建て**（`USD` `米ドル` など）。円換算のレート・基準日・出典の保存場所が無いため、換算せず `null`。為替レートの推定で円換算しない。
- **掲載文に金額（`○円` `○千円` `○万円` `○ポイント`）が 1 つも出てこないもの**。自社商品の相場を常識で見積もって入れない（取り込んだ金額は公開面で企業が示した額として表示されるため）。

### 取り込みで機械的にはじかれる金額

すべての非 null 金額は、要約と無関係に掲載文・保存見出し・実際の株数と権利月を
使う共有厳密判定を通ります。低額でも、円の数字があるだけでは通りません。
掲載文に複数の額面や保有条件が並び、1回分の全体額を一意に決められなければ `null` にしてください。

- 掲載文が割引・値引きで、金券の表現（`円分` `円相当` `円券` `QUO` `ギフトカード` `商品券` `カタログギフト` など）が無いのに、金額を入れた。
- 掲載文に金額（`○円` `○千円` `○万円` `○ポイント`）が 1 つも無いのに、金額を入れた（`value_ungrounded`）。
- **50,000 円以上**には既存の過大値検査も適用される。ただし、この検査に通っても共有厳密判定の代わりにはならず、任意の合計・概算・別条件の額面は採用しない。
- 抽選の賞品表記なのに、金額を入れた（`value_guard`）。「抽選」を含む掲載文で、金額が当選人数つき（`各○名` `○名に` `○○円相当:○名`）か、賞品表つきの「総額○○円」と一致するもの。この補助検査を通っても優待全体の会社額面が認定されたことにはならず、共有厳密判定を別に必要とする。
- 外貨額面（`USD` `USドル` `米ドル`）と一致し、円の金額表現と一致しない値を入れた（`value_guard`）。低額でも見る。

金額でひっかかった行は、要約も含めて行ごとはじかれます（要約側も読み違えている疑いが強いため）。

## 8. 取り込みがはじく理由の一覧

検証結果の出力（`はじいた結果` の一覧）には、既定では掲載文や要約本体
そのものを出しません。`contract` の詳細は破った規則名と字数だけ、`parse`（JSON
として読めない行）の詳細も固定文で、Node の元エラー文（入力の先頭が乗ることがある）
は出しません。本文を見て直したいときは `--show-text` を付けると端末にだけ出ます
（`pnpm yutai:summary:import ... --show-text`）。既定でオフなので、この出力先を
Issue / PR / チャット等の公開・共有される場所に貼らないでください（1 章参照）。

| reason | 意味 | 直し方 |
|---|---|---|
| `parse` | JSON として読めない | 1 行 1 オブジェクトにする |
| `schema` | キーの過不足・型違い・`estimatedValue` が 0 以下や小数 | 4 つのキーだけを正しい型で書く |
| `duplicate` | 同じ `taskId` が複数行ある | 1 タスク 1 行にする |
| `unknown_task` | 渡したタスクファイルに無い `taskId` | `taskId` を書き換えない |
| `contract_version` | 版が現行と違う | 最新のタスクファイルと最新のこの文書で作り直す |
| `stale` | タスク発行後に掲載文が変わった | 新しくタスクを書き出して作り直す |
| `contract` | 5 章の規則違反 | 規則に沿って短く書き直す |
| `verbatim` | 掲載文の 40 字以上の書き写し | 自分の言葉で短くする |
| `summary_conditions` | 選択・保有・抽選・応募の重要条件が欠落 | 同じ条件を要約に残す |
| `summary_ungrounded` | 要約の単位付き数値が掲載文・実受取条件と一致しない | 掲載文・同じ受取条件の数値と単位で書き直す |
| `value_guard` | 6 章の金額ガードに該当 | 金額を見直すか `null` にする |
| `value_ungrounded` | 掲載文に金額表現が無いのに金額を入れた | `null` にする |
