# EDINETコードリストの基準日と行検証

## 原因と修正

`fetch_codelist` が原本の `data_date` に取得当日を設定する一方、マスタの provenance はCSVメタ行の公表基準日を使っていた。同じ原本の日時が経路によって変わるため、原本保存もメタ行を使用する。日付がない原本は既存の `None` / `nodate` とし、取得当日を補わない。`fetched_at` は既存の取得時計として別に保存する。

業種同期の `_scan_listed_rows` はマスタの `parse_codelist` とCSVを別に走査し、マスタが許容する完全な空白行で添字エラーになっていた。ヘッダ一意性・必須列・非空行の列幅検証を既存collector内の同じreaderにまとめ、両経路が使う。非空行の欠落・余分列の拒否と元の行番号は維持する。

全callerを検索した。マスタ同期・業種同期がこのcollectorを使う。他のEDINET文書collectorは開示日を使っており、取得当日を設定する同じ誤りはなかった。

## 検証

- Nixの既存pytestでコードリスト・業種同期92件が成功。
- Pythonパイプライン全体のpytestが成功。未取得の実フィクスチャは既存規約に従い明示skip。
- 変更4ファイルのruffが成功。
- 実取得した2026-06-10の原本が、実行日によらず20260610の原本名と基準日で保存されることを確認。
- 同じ実原本のメタ行だけを欠落させ、日付を推定しないことを確認。
- 同じ実原本に完全な空白行だけを追加し、マスタと業種走査の全結果が元原本と一致することを確認。
- 独立レビューで、日付解読の例外が原本保存より前に出る変更を検出。保存をfinallyで保証して例外を伝播し、実原本のCSV名だけを壊したZIPが無加工で残る回帰テストを追加。

本検証はローカルのみ。外部取得・本番書き込みは行っていない。新規上場3銘柄のコードリスト上の識別子欠損・上場区分不一致は、この日時・行検証の修正では解消したと扱わない。
