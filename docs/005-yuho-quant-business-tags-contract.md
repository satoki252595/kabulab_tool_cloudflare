## 3. 不変条件

- `事業タグの状態 = 判定済` ⇔ `事業タグの根拠書類` の書類 ID = `有報書類ID`
  **かつ** `単語帳の版` = その判定に使った版。書類が新しくなったら、タグは新しい書類で
  判定し直してから `判定済` にする（古い書類のタグを新しい書類のものとして見せない）。
- `事業タグ（素材・部品・装置）` / `事業タグ（製品・サービス）` / `事業タグ（流通・サービス）` / `投資テーマ` に入るのは
  **判定でコードが抜き出した実文に基づく AI 判定結果**か、そこからの決定的導出のみ。
  これらの列に入る値・要確認タグの語・根拠の引用文は AI の作文ではない（設計 §1）。
- 本文列（39 項目）は EDINET 原文の**そのままの抜粋**（PDL1.0・出典表示のもと利用）。

## 4. 状態列の読み方（誤読注意: `未判定` ≠ `該当なし`）

**`事業タグの状態 = 未判定` は「まだ判定していない」であり、「タグに該当する事業が無い」
ではない。** `未判定` の行の `事業タグ（素材・部品・装置）` 等が空でも、それは「無い」と
確定した情報ではなく「わからない」。この行を**スクリーニングの除外条件に使わない**こと
（「該当銘柄が無い」という誤った結論を導く）。

各値の意味（`本文の状態` と `事業タグの状態` は独立列。両方見ること）:

| `事業タグの状態` | 意味 | タグ列の扱い |
|---|---|---|
| `判定済` | jev 判定が完了し、上表§3の不変条件を満たす | 信頼してよい（該当が無ければ空配列が正しい） |
| `未判定` | まだこの銘柄の判定を実行していない | **不明として扱う**（除外条件に使わない） |
| `本文なし` | 対象の有報に「事業の内容」等の本文が無い/取得できない | タグ列は空。「タグ無し」ではなく「判定不能」相当 |
| `読込失敗` | 補足行への本文同期そのものが失敗した | 同上。`次回再試行日` を過ぎれば自動で再試行される |
| `判定不能` | jev 呼び出しが最終的に失敗した（既定値で埋めていない） | 同上 |

同様に `本文の状態` も `取得済` 以外は本文列が空でも「非開示」と断定しない（取得未実施の
可能性を含む）。

## 5. 読み方（Notion API）

- `GET /v1/databases/{database_id}` でスキーマを取得し、必要な列の `property id` を控える。
- `POST /v1/databases/{database_id}/query` に **`filter_properties`**（必要な列の property id
  の配列）を付けてクエリする。39 本文列は 1 行あたり合計で大きくなり得るため、**タグ関連の
  メタ列だけ**（銘柄コード・33業種・各タグ列・状態列・判定日・単語帳の版）を基本とし、
  本文そのものが必要なとき（根拠の元文を遡って読みたい等）だけ本文列を個別に足す。
- ページネーション必須（`has_more` / `next_cursor`）。
- Notion-Version ヘッダは `2022-06-28`。

## 6. 現在のタグの導出方法

1. `事業タグの状態 = 判定済` の行だけを対象にする（§4）。
2. 「保有する事業タグ」= `事業タグ（素材・部品・装置）` ∪ `事業タグ（製品・サービス）`
   ∪ `事業タグ（流通・サービス）`（いずれの列も multi_select の値＝単語帳の `labelJa`）。
3. 「該当する投資テーマ」= `投資テーマ` 列の値（すでに決定的導出済みなので、そのまま使う。
   自前で member 展開をやり直す必要は無い）。
4. 語の意味（定義）を厳密に知りたい場合は、単語帳そのもの（§8）の該当 `id`/`labelJa` の
   `definitionJa` を引く（列の値である `labelJa` だけでは短すぎることがある）。
5. `要確認タグ` は「はい」と確定していない語なので、既定では 4 の集合に含めない
   （含める場合は「要確認」であることを明示して使う）。

## 7. 根拠（引用文）の場所

タグの根拠（当たった原文の文・確率・出典書類）は**行のプロパティではなく、そのページの
本文**にある。ページ本文にトグル見出し（heading_3, toggleable）が 1 つあり、タイトルは

```
事業タグの根拠（単語帳 vX・有報 S100XXXX 2025年3月期）
```

の形（`X`=単語帳の版、`S100XXXX`=書類 ID、`2025年3月期`=会計期末の和暦表記）。子要素に
語ごとの引用ブロック（quote block）が 1 つずつあり、1 行目が
`<語名>（はい 0.93）` または `要確認: <語名>（確認不能 0.55）`、続く行が
`「<原文の引用>」 — 有報 <書類ID> <期末>「<項目名>」` の形。**このトグルの中身だけ**が
根拠であり、行プロパティにはこの引用文は入らない（`要確認タグ` 列にあるのは語名+確率のみ）。

再判定時はこのトグルを作り直す（削除→新規作成）ので、**トグルのブロック ID をキャッシュ
しないこと**（判定し直しの度に変わる）。

## 8. 単語帳（語彙）の出所

タグ付けに使われた単語帳の**正本**は、同じ「株式情報」ページ配下の別データベース
**`事業タグ単語帳（台帳）`** にある。

- 「種別 = 版」かつ「状態 = 有効」の行が**ちょうど1つ**存在し、それが現在有効な単語帳。
- その行のページ本文は、目印の見出し（heading_2「記録本文（JSON）」）の後に、単語帳全体の
  JSON が code block（2,000 字ごとに分割）で続く。code block の文字列を順に結合すると
  1 つの JSON になる。
- 行のプロパティ「ハッシュ」に、その JSON（正規化: キー順固定・空白無し）の SHA-256 (hex)
  が入っている。**読むときは必ずハッシュを照合し、不一致なら使わない**（Notion 上の手動
  編集による改ざん・破損を検知するため）。
- 単語帳 JSON の中の `business[].id` / `labelJa` が、`銘柄マスタ（補足）` の multi_select
  の値（`labelJa`）と対応する。`themes[].id` / `labelJa` も同様。
- 版が上がる（`v1` → `v2` 等）と、旧版の行は「状態 = 置換済」になり、新しい行が
  「状態 = 有効」になる（履歴は消えない。台帳を辿れば過去の単語帳もすべて復元できる）。

## 9. 変更告知ポリシー

以下は kabulabAgents に**事前告知が必須**（このリポジトリの PR 説明・Notion への通知等、
運営が実際に伝えられる経路で）:

- `銘柄マスタ（補足）` の**列の改名・型変更・削除**（追加は告知不要。破壊的変更のみ対象）
- `事業タグの状態` / `本文の状態` / `書類種別` の**選択肢の意味変更**（新しい選択肢の追加は
  告知不要。既存の選択肢の意味を変えることは実質的な破壊的変更）
- `事業タグ単語帳（台帳）` の列構成の変更
- 単語帳 JSON のトップレベルの形（`version` / `business[]` / `themes[]`）の変更
  （`business[]`/`themes[]` の中身が増減するのは通常運用であり告知不要。**形自体**の変更のみ対象）

上記に該当しない変更（銘柄の追加、タグの再判定、単語帳への語の追加・廃止、選択肢の
新規追加）は通常運用であり、都度の告知はしない。
